The Big Moment

What happens in the seconds after you click Start Debate

What You Already Know

Imagine an online debate show where AI debaters argue about any topic in real-time. You type a topic like "Should AI replace teachers?", pick your debaters, and watch them go. You have already used the app. Now let us look at what is actually happening behind the screen.

The app has two halves. The frontend is everything you see and click. The backend is the behind-the-scenes worker that talks to AI models, manages the debate, and streams results back.

🟢
Proponent (正方)

The passionate supporter. Builds strong arguments, cites success stories, and faces criticism head-on.

🔴
Opponent (反方)

The sharp critic. Finds logical flaws, demands evidence, and attacks the weakest links.

🔵
Analyst (分析家)

The data-driven thinker. Weighs multiple perspectives, asks "by what standard?", and lets numbers speak.

These three debaters are defined in a file called presets.yaml. Each one has a name, a stance (for/against/neutral), and a personality description that shapes how they argue. You can also create custom debaters through the app.

💡
Aha moment

A web app is basically a conversation between two programs: the frontend (what you see) and the backend (the behind-the-scenes worker). When you click a button, the frontend sends a message to the backend, the backend does the work, and sends a message back. Everything else is just making that conversation smoother.

The Journey Begins

Here is exactly what happens when you click "Start Debate," broken into five steps. Each step involves either the frontend or the server doing a specific job.

1
Frontend sends a POST request to /api/debate/start

The frontend bundles your topic, chosen debaters, and max rounds into a JSON payload and sends it to a specific URL (called an endpoint) on the backend.

2
Backend creates a DebateEngine with the topic and debaters

The server receives the request, looks up the full debater profiles from presets, and passes them to the DebateEngine — the core object that manages the entire debate.

3
Backend initializes debate state

The DebateEngine sets up a round counter, turn order (who speaks when), and an empty message history. The debate is now "active" but no one has spoken yet.

4
Frontend opens an SSE connection to /api/debate/stream

Instead of asking "is it done yet?" over and over, the frontend opens a persistent connection so the server can push new content the instant it is ready.

5
SSE connection triggers ensure_loop_running()

This is the clever part. The debate loop does not start when you click the button — it starts when the frontend is actually listening. That way, no words get lost.

Python · main.py @app.post("/api/debate/start") async def start_debate(config: DebateConfig): if len(config.debater_names) < 2: raise HTTPException( status_code=400, detail="At least 2 debaters required" ) all_debaters = load_presets() + custom_debaters debater_map = {d.name: d for d in all_debaters} selected = [debater_map[name] for name in config.debater_names if name in debater_map] debate_engine.start(config.topic, selected, config.max_rounds) return {"status": "started", "topic": config.topic}
What this means
Register this function as a POST endpoint at /api/debate/start
Name the function start_debate and expect a DebateConfig object (topic, debater names, max rounds)
Make sure at least 2 debaters were selected — otherwise return an error
Gather all available debaters (presets + any custom ones)
Look up each selected debater by name to get their full profile (personality, stance, color, etc.)
Tell the DebateEngine to begin — pass in the topic, the selected debaters, and the round limit
Send back a confirmation: {"status": "started", "topic": "..."}

Meet the Cast

The actors that make the debate happen

The Cast of Characters

Every app is built from pieces that each do one job well. Think of them as actors in a play — each has a role, a script, and a place on stage. Here are the five main characters in our app.

⚙
DebateEngine

The referee. Lives in debate_engine.py. Runs the debate loop, tracks state, and manages whose turn it is. Like a debate moderator who also runs the scoreboard.

★
Agents

The debaters' brains. Each agent in agents.py knows its stance, personality, and has tools like web search. Like giving each debater a brain transplant with a different personality each time.

🔍
Web Search Tool

The research assistant. tools.py searches Brave Search and returns results. Has a built-in rate limiter (max 1 search per second) so it stays polite.

🔗
FastAPI Server

The switchboard operator. main.py routes incoming requests to the right endpoint, serves the frontend, and manages SSE connections.

🎬
Frontend

The stage. app.js + index.html render the debate in real-time using SSE events. Handles debater selection, drag-to-reorder, and renders markdown into styled text.

💡
Key Insight

Every piece of software has a "separation of concerns" pattern — each file handles one job. main.py handles HTTP requests, debate_engine.py handles debate logic, agents.py handles AI personalities, and tools.py handles external searches. When you need to change something, this separation tells you exactly where to look. This pattern is the #1 thing that helps you steer AI coding tools effectively — you can say "put this logic in the engine, not the API layer" and get better code.

How Messages Flow

Real-time streaming: the invisible conveyor belt

The Live Connection

Imagine a stock ticker — you open one connection and prices keep flowing in without you ever refreshing. SSE works the same way: the browser opens one long-lasting connection, and the server pushes new data through it whenever it is ready.

In a normal HTTP request, you ask a question and wait for the full answer. With SSE, you open a channel and the server keeps sending updates as they happen — like turning on a faucet instead of filling a bucket.

This is what makes the debate feel real-time. Every word the AI generates gets streamed to your screen the instant it is ready. No waiting, no page reloads.

💡
Good to know

SSE is one of three ways to build real-time web apps. The other two are WebSockets (two-way, like a phone call) and polling (asking repeatedly, like checking your mailbox). SSE is perfect here because the debate is one-directional — the server sends data to the browser, but the browser never needs to send data back through the same channel. It is simpler and more reliable than WebSockets for this use case.

The Event Types

The SSE connection carries different types of messages, called events. Each event has a type (a label) and a payload (the content). Here are all 11 types the debate uses.

debater_start A debater is about to speak. Contains their name, color, and avatar.
thinking_chunk A piece of the AI's internal reasoning. Shown in the collapsible thinking section.
debater_finalize The AI finished thinking. Collapses the thinking section.
debater_chunk A piece of the debater's actual argument. Displayed word by word on screen.
debater_end The debater finished their turn. Contains the full text of their argument.
tool_call The debater used the web search tool. Shows the search query and a summary of results.
round_end One complete round finished (all debaters spoke). Contains the round number.
debate_end The debate is over. Sent when max rounds are reached.
debate_paused The user paused the debate. The SSE connection closes.
judge_chunk A piece of the judge's analysis. Streamed word by word like debater chunks.
judge_result The judge finished their analysis. Closes the SSE connection.

Think of each chunk as a single word on a conveyor belt. The server puts words on the belt one at a time, and the browser picks them up and displays them as they arrive.

The SSE Endpoint — Code Translation

Here is the actual code that keeps the SSE connection alive. It lives in main.py. The left side is real Python; the right side is what each part means in plain English.

Python · main.py async def event_generator(): if debate_engine: debate_engine.ensure_loop_running() while True: if debate_engine and debate_engine.state: try: event = await asyncio.wait_for( debate_engine.event_queue.get(), timeout=30.0 ) data = json.dumps(event.payload) yield f"event: {event.type}\ndata: {data}\n\n" if event.type in ( "debate_end", "judge_result", "debate_paused" ): break except asyncio.TimeoutError: yield ": keepalive\n\n"
What this means
If the debate engine exists, start the debate loop running in the background...
Keep this connection open forever (or until the debate ends)...
Wait up to 30 seconds for the next event from the queue...
Convert the event data to JSON text and send it in SSE format: first the event type, then the data...
If the event means the debate is over, close the connection. Otherwise, keep listening...
If nothing happened for 30 seconds, send a keepalive ping so the connection does not time out...

The key pattern is the async loop. It waits for events with a timeout of 30 seconds. If an event arrives, it gets sent immediately. If nothing arrives, a keepalive ping prevents the connection from being closed by a proxy or browser.

The Art of Prompts

How each debater gets a unique personality — and why it changes every turn

Two Kinds of Prompts

Imagine a theater director giving each actor personalized notes before every scene — not just at the start of the play. Before each debater speaks, the app sends two separate messages to the LLM. Each serves a different purpose.

🎭
System Prompt (the personality)

"Who you are, what you believe, how you should behave." This tells the AI its role — supporter, critic, or analyst. It includes the rules of debate, the current round number, and the debater's unique personality. It is rebuilt from scratch before every single turn.

💬
User Prompt (the situation)

"Here is what is happening right now." This delivers the debate topic and what everyone else has said so far. It changes every turn as the debate evolves. Think of it as the director saying "here is where the story has reached — now say your line."

The system prompt defines identity. The user prompt delivers context. Together, they give the AI everything it needs to play its part.

The 5-Part Recipe

The system prompt is not one big block of text. It is assembled from separate ingredients, like a recipe. A function called _build_debater_instructions combines these parts every time a debater takes a turn.

1
Date context

"Today is 2026-04-03. The current year is 2026." This goes first so the AI knows what "recent" and "current" actually mean. Without it, the AI might cite outdated information.

2
Debate rules

The shared rules every debater follows: be concise, respond to others, use [[Name]] for mentions, no bare assertions, no personal attacks. These are the same for everyone.

3
Stance

"You support the topic" (正方) or "You oppose the topic" (反方) or "You take a balanced view" (中立). This is the debater's team assignment — which side they argue for.

4
Personality

The unique persona from presets.yaml: "你是正方——你的职责是为辩题提供有力支撑..." This is what makes each debater sound different from the others.

5
Search instructions (if enabled)

Round 1: search actively for facts. Round 2+: conserve, max 1 search per round. Only debaters with search capability get this part. The analyst, for example, skips it entirely.

6
Round countdown

"This is round 3 of 10. There are 6 rounds remaining." Or on the last turn: "FINAL ROUND. Make your strongest closing argument." This is why the prompt must be rebuilt every turn — the countdown changes.

These parts are joined with a separator line (\n\n---\n\n) to create one complete instruction block. The result is a fresh, context-aware system prompt for every single turn.

The Builder Function

Here is the actual code that assembles the system prompt. On the left is the Python function. On the right is what each line does in plain English.

Python · agents.py def _build_debater_instructions(ctx: RunContext[DebaterDeps]) -> str: debater = ctx.deps.debater stance = STANCE_INSTRUCTIONS.get(debater.stance, ...) now = datetime.now() date_context = ( f"**CURRENT DATE: {now.strftime('%Y-%m-%d')}**\n" f"The current year is **{now.year}**." ) parts = [ date_context, DEBATE_RULES, f"Your stance: {stance}", debater.personality, ] if debater.enable_search: parts.append(SEARCH_INSTRUCTIONS) if ctx.deps.max_rounds: remaining = max_r - ctx.deps.round_number if remaining <= 1: parts.append("FINAL ROUND...") else: parts.append(f"round {current} of {max_r}...") return "\n\n---\n\n".join(parts)
What this means
This function builds the system prompt from scratch every time a debater takes a turn. The RunContext carries all the info it needs.
Look up what stance this debater has: supporter (正方), opponent (反方), or neutral (中立).
Get the current date so the AI knows what "recent" means when it talks about events.
Start assembling the parts: today's date, the shared debate rules, the debater's stance, and their unique personality.
If this debater has search enabled, add the search strategy instructions too.
If there are limited rounds, add a round countdown — or "FINAL ROUND" if it's the last one.
Join all parts with a separator line. The result is one complete system prompt — a string of text ready to send to the AI.

Notice how the function uses dependency injection — the ctx object carries everything in. The function never reaches out to find the debater's name or the round number. It simply unpacks what was handed to it.

The User Prompt — What Goes In

While the system prompt defines who the AI is, the user prompt tells it what is happening. A separate function called _build_user_prompt constructs this every turn. Here is how it works.

Python · debate_engine.py def _build_user_prompt(self, debater: Debater) -> str: if not self.state.history: return ( f"You are the first speaker. " f"No one has spoken yet - do NOT reference " f"or quote anyone. Present your opening " f"argument on the topic: {self.state.topic}" ) parts = [f"Debate topic: {self.state.topic}"] for msg in self.state.history: if msg.speaker == debater.name: continue parts.append(f"[{msg.speaker}]: {msg.content}") return "\n\n".join(parts)
What this means
If this is the very first turn and no one has spoken yet, give a special opening prompt with just the topic.
Otherwise, start by restating the debate topic so the AI always knows what it's arguing about.
Go through every message in the debate history so far, one by one.
Skip this debater's own past messages — those are already in the AI's memory through PydanticAI's built-in message history.
Include everyone else's messages so the debater can respond to them.
Join everything into one string and send it as the user prompt.

The clever part is the skip. A debater's own past messages are already stored in PydanticAI's internal message history (self._history). So the user prompt only needs to include what other people said. This avoids repeating the debater's own words back to it.

💡
Key Insight

The split between system prompt and user prompt is the most important concept in AI app design. The system prompt defines WHO the AI is. The user prompt defines WHAT'S HAPPENING right now. When you are building AI apps, the system prompt is your "configuration" and the user prompt is your "data." This separation lets you change the AI's behavior (system prompt) without changing the situation (user prompt), and vice versa. This is the foundation of all prompt engineering.

Patterns Worth Knowing

Every codebase has a few clever tricks tucked inside. Here are three worth remembering — not because you need to memorize them, but because they show up in almost every web app.

⏱
Rate Limiting

The web_search tool in tools.py has a built-in rate limiter: max 1 request per second. It uses an asyncio Lock so only one search runs at a time, even if multiple debaters search simultaneously. This prevents overwhelming the Brave Search API and getting your key revoked.

▦
CSS Grid Collapse

The thinking sections and tool cards use a CSS Grid trick for smooth collapse animation: grid-template-rows: 1fr (open) transitions to grid-template-rows: 0fr (closed). This avoids the janky max-height animation hack that most web apps use.

📑
Per-Debater Memory

Each debater has its own message_history dictionary (self._history) in debate_engine.py. After each turn, the full PydanticAI conversation is stored so the debater remembers what it said before — without it appearing in the user prompt sent to other debaters.

Debugging Intuition

When something breaks, here is where to look. Think of this as your troubleshooting cheat sheet.

🔌
Messages not appearing

Check the SSE connection in connectSSE() (app.js) and the event_generator() in main.py. The SSE stream must be open before ensure_loop_running() is called — otherwise words get generated with no one listening.

🧠
Debater says wrong things

Check the system prompt assembly in _build_debater_instructions() (agents.py). Is the stance correct? Is the personality loaded? Is the round number right? The prompt is rebuilt from scratch every turn.

🔍
Web search not working

Check the BRAVE_API_KEY in .env and the rate limiter in tools.py. The _limiter.acquire() call might be blocking if searches pile up from multiple debaters.

📝
Formatting looks broken

Check the renderContent() method in app.js. It uses marked.js to convert Markdown to HTML, and has special handling for [[Name]] mention patterns.

⏸
Debate won't resume

Check that resume() sets state.active = True and that the frontend reconnects SSE. The loop only runs when state.active is True AND the SSE consumer is connected. Both conditions must be met.

The Config That Runs It All

Everything the app needs to run lives in a single file called .env. Here are the four settings that control the entire system.

API_BASE_URL The address of the LLM server (default: DeepSeek's API)
API_KEY Your secret key for the LLM provider
MODEL Which AI model to use (default: deepseek-reasoner)
BRAVE_API_KEY Key for Brave Search (optional — search is disabled without it)

The config.py loads these using python-dotenv's dotenv dotenv_values, which reads the .env file without touching the system environment variable space. This means your API keys stay in the .env file and don't leak into your terminal history.

The module load time matters: config.py creates a single Settings() instance when the server first starts. To pick up changes to your .env file, you need to restart the server.

📖
Good to know

This project works with any OpenAI-compatible API, not just DeepSeek. You can point it at a local model running in Ollama, a self-hosted vLLM server, or even OpenAI itself. Just change API_BASE_URL and MODEL in your .env file. This flexibility comes from using the OpenAI SDK standard — one of the most widely adopted API formats in the AI world.
